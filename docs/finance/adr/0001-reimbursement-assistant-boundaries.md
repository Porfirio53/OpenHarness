# ADR-0001：报账助手 MVP 的系统边界与决策责任

- 状态：Accepted for MVP
- 日期：2026-07-16
- 决策范围：首月独立开发

## 背景

报账助手需要把自然语言需求转换为可复现的报账前置检查。财务制度包含必需材料、条件
材料、字段依赖、预算和资金闸门；文档之间还存在版本差异。模型生成的答案具有不确定性，
无法独立承担硬性合规判断。OpenHarness 已经提供会话、工具循环、权限和项目插件机制，
领域实现无需复制这些基础能力。

## 决策

首月 MVP 只支持国内差旅费、会议费和 IT 维护支撑费正式报账三个场景。未知场景、低
置信输入、关键证据不可读和来源冲突统一进入澄清、阻断或人工复核，系统不猜测结论。

预算项目确认和资金计划确认位于材料检查之前。任一前置条件不满足时，系统返回稳定的
阻断原因和后续处理方向，不继续输出“材料齐全”结论。

硬性要求由不可变、带版本的规则包执行。每条材料或字段规则必须包含规则 ID、受控条件、
严重级别、用户提示和可定位的 `ProcessReference`。LLM 仅可用于歧义分类、非结构化文字
抽取和基于已检索证据的解释；LLM 结果不能覆盖确定性规则。

来源冲突按以下优先顺序处理：最新且已生效并经财务确认的制度；最新业务场景与业财/现金
流映射；预算流程和预算问答；报账系统操作手册；由上述资料生成的索引或问答。缺版本、
缺生效日期或无法定位的规则进入 `review_required`，不能激活。当前 2025V1 成本费用域手册
优先于 2023 年系统操作手册中的冲突内容。

报账领域代码保持在 `openharness.finance_harness.reimbursement_assistant`。只有
`integration/` 和项目插件薄适配器可以导入 OpenHarness 接口；分类、规则和检查服务不依赖
QueryEngine、UI 或会话内部对象。接入工具只做输入校验、服务调用和错误映射，全部标记为
只读。项目插件在设置中显式批准后启用。

审计事件只记录会话标识、阶段、决策、原因码、规则包版本、规则 ID 和脱敏元数据。Git 只
保存合成数据。原始制度、票据、账号、用户附件、截图和生产日志留在批准的内部存储中；
未经批准不得发送至外部模型。

新文档只能生成候选规则包。候选包经过 Schema 校验、来源存在性检查、冲突检查、黄金集
回归和财务人工批准后才能成为 `active`；发布通过新版本完成，并保留回滚目标。

## OpenHarness 接入依据

在参考提交 `9b2efd7` 中，工具继承 `BaseTool` 并声明名称、描述、Pydantic 输入模型、异步
`execute` 和只读属性；项目插件能够发现插件 `tools/` 下的工具类，且项目插件默认禁用。
因此 MVP 采用项目插件薄适配，不修改 QueryEngine、默认 ToolRegistry 或插件加载器。

## 后果

这项决策提高了可追溯性、回归稳定性和故障时的保守性，同时要求先人工编译三个黄金规则
包。首月不覆盖全量业务场景、真实 ERP 写入、税务最终判断、自动规则发布、生产级知识库、
图片识别和批量模板填充。

## 验证

- `schemas.py` 能表达置信度、阻断原因、规则版本、证据定位和审计事件；
- 20 条合成验收契约覆盖三个试点场景、预算/资金闸门及安全回退；
- OpenHarness 上游核心文件零改动；
- 领域测试、Ruff、Mypy、完整回归和前端类型检查由基线脚本记录。
